## 1. 프로젝트 개요

본 과제는 1번부터 100번까지 총 100개의 좌석을 관리하는 멀티스레드 예약 서버(`pa3_server`)와, 이 서버에 TCP로 접속해서 사용자 입력을 요청으로 변환·전송하고 응답을 출력하는 클라이언트(`pa3_client`)를 C로 구현한다. 서버는 여러 클라이언트가 동시에 접속하여 회원가입/로그인, 좌석 예약, 예약 확인, 예약 취소, 로그아웃, 좌석 통계 조회를 수행할 수 있도록 지원한다.

가장 중요한 설계 요구사항은 다음 세 가지이다.

- **동시성 안전성**: 서버는 CPU 코어 수만큼의 워커 스레드를 두고, 각 워커가 자신에게 배정된 클라이언트 소켓을 `poll`로 감시한다. 한 사용자가 동시에 두 클라이언트에 로그인할 수 없고, 두 클라이언트가 같은 좌석을 동시에 예약하려고 하면 한 쪽만 성공해야 한다.
- **자원 정리**: 동적 할당 메모리, 파일/소켓, mutex, 스레드, 자식 프로세스 등 모든 자원이 종료 전에 해제되어야 한다. PDF 명세에서 `valgrind --leak-check=full --track-origins=yes --show-leak-kinds=all`로 검증한다고 명시하고 있다.
- **명세된 출력 포맷 준수**: 성공은 stdout, 실패는 stderr로 분리하고, 메시지 문자열도 명세와 정확히 일치해야 한다.

본 보고서는 위 요구사항을 만족시키기 위해 세운 설계 결정과 구체적인 구현 방법을 정리한다.

### 2.2 컴파일 옵션과 라이브러리

루트 `Makefile`은 다음과 같다.

```make
CC=gcc
CFLAGS=-Wall -Wextra -Wpedantic -Werror -ggdb -std=gnu2x -D_GNU_SOURCE -Iinclude
```

- `-Werror`: 경고도 모두 실패로 처리한다.
- `-D_GNU_SOURCE`: `sched_getaffinity`, `getrandom` 등 GNU 확장 API를 사용하기 위해 필요하다.
- `-std=gnu2x`: 스켈레톤에 사용된 `nullptr` 등 C2x 키워드를 지원하기 위함이다.

서버는 `-l:libargon2.so.1` 또는 `-largon2`로 Argon2를 동적 링크한다. 시스템에 따라 `.so` 이름이 다른 환경(우분투 22.04/24.04 등)을 모두 지원하기 위해 `server.mk`에서 다음과 같이 자동으로 선택한다.

```make
ARGON2_LDLIBS := $(shell if ldconfig -p 2>/dev/null | grep -q 'libargon2\.so '; \
                  then printf '%s' '-largon2'; \
                  elif ldconfig -p 2>/dev/null | grep -q 'libargon2\.so\.1'; \
                  then printf '%s' '-l:libargon2.so.1'; \
                  else printf '%s' '-largon2'; fi)
```

클라이언트는 interactive mode에서 `readline`을 사용하기 위해 `-ledit`을 링크한다.

### 2.3 실행 방법

명세대로 다음과 같이 실행한다.

```sh
$ ./pa3_server <port>
$ ./pa3_client <ip_address> <port>           # interactive mode
$ ./pa3_client <ip_address> <port> <file>    # file mode
```

`make` 후 `ls | grep pa3`에서 `pa3_server`, `pa3_client`가 모두 보이는 것을 확인할 수 있다.

## 3. 통신 프로토콜 설계

### 3.1 자료구조

`include/helper.h`에 정의된 `Request`/`Response`는 다음과 같다.

```c
typedef struct {
  uint64_t username_length;
  uint64_t data_size;
  Action   action;
  char*    username;
  char*    data;
} Request;

typedef struct {
  uint64_t data_size;
  int32_t  code;
  uint8_t* data;
} Response;
```

포인터 필드(`username`, `data`)는 프로세스마다 의미 있는 값이 다르기 때문에 구조체를 그대로 `write`할 수는 없다. 그래서 PA3 명세가 권장한 TLV(Type-Length-Value) 방식을 따라, 각 필드를 정해진 순서로 개별 전송한다.

### 3.2 전송 순서

**Request (클라이언트 → 서버)**

| 순서 | 필드 | 크기 |
|---|---|---|
| 1 | `action`            | `sizeof(Action)` (4 byte) |
| 2 | `username_length`   | 8 byte |
| 3 | `data_size`         | 8 byte |
| 4 | `username` (가변)   | `username_length` byte (있을 때만) |
| 5 | `data` (가변)       | `data_size` byte (있을 때만) |

**Response (서버 → 클라이언트)**

| 순서 | 필드 | 크기 |
|---|---|---|
| 1 | `code`              | 4 byte |
| 2 | `data_size`         | 8 byte |
| 3 | `data` (가변)       | `data_size` byte (있을 때만) |

길이를 데이터보다 먼저 보내기 때문에, 받는 쪽은 가변 길이 필드를 받기 전에 필요한 크기만큼 `calloc`/`malloc`으로 버퍼를 준비할 수 있다. `null terminator`를 위해 username/data는 길이보다 1 byte 크게 할당한다.

### 3.3 `safe_read`/`safe_write`

TCP는 1번의 `read`/`write`로 요청한 바이트가 모두 전송된다는 보장이 없고, signal로 중단될 수도 있다. `common/helper.c`의 `safe_*`는 다음을 반복 수행한다.

- 부분 전송이 발생하면 남은 양만큼 다시 호출한다.
- `EINTR`로 실패하면 다시 시도한다.
- `read`가 0을 반환하면(상대 close) 그 시점까지 읽은 바이트 수를 반환한다.
- 그 외 오류는 -1을 반환한다.

서버의 `receive_request`/`send_response`와 클라이언트의 `send_request`/`receive_response` 모두 `safe_*`만 사용한다. `pa3_client.c`에서는 더 나아가 `write_or_exit`/`read_or_exit` 래퍼로 감싸서, 부분 전송/오류가 발생하면 즉시 `perror` 후 종료하도록 했다.

### 3.4 응답 데이터 포맷

- `confirm-booking`의 응답 data는 `pa3_seat_t(=uint64_t)` 배열이다. 클라이언트가 `response->data`를 `(pa3_seat_t*)`로 캐스팅해서 좌석 번호를 출력한다.
- `query`의 응답 data는 `SeatStats` 구조체를 그대로 byte sequence로 보낸다. 구조체에 포인터가 없으므로 안전하다. 클라이언트는 `memcpy`로 복사한다.

## 4. 서버 아키텍처: 메인 스레드와 워커 스레드

### 4.1 전체 그림

```
                          ┌─────────────┐
                          │ main thread │
                          │  ┌────────┐ │
                          │  │ poll() │ │  stdin + listen socket
                          │  └────────┘ │
                          └──────┬──────┘
                                 │ accept → find_suitable_pollset
                                 │ add_to_pollset + notify(pipe write)
        ┌────────────────────────┼───────────────────────────┐
        ▼                        ▼                           ▼
┌───────────────┐        ┌───────────────┐           ┌───────────────┐
│ worker thread │        │ worker thread │   ......  │ worker thread │
│  ┌─────────┐  │        │  ┌─────────┐  │           │  ┌─────────┐  │
│  │ PollSet │  │        │  │ PollSet │  │           │  │ PollSet │  │
│  └─────────┘  │        │  └─────────┘  │           │  └─────────┘  │
│  pipe_out_fd  │        │  pipe_out_fd  │           │  pipe_out_fd  │
└───────────────┘        └───────────────┘           └───────────────┘
        │                        │                           │
        └────────────────┬───────┴───────┬───────────────────┘
                         ▼               ▼
                  ┌─────────────┐ ┌─────────────┐
                  │   Users     │ │   Seats     │  공유 자원
                  └─────────────┘ └─────────────┘
```

### 4.2 메인 스레드의 역할

`main()`(server/pa3_server.c)은 다음 순서로 동작한다.

1. `setup_sigint_handler()`로 SIGINT 핸들러를 설치한다.
2. `setup_users(&users)`로 사용자 배열·mutex 배열을 초기화한다.
3. `default_seats()`로 좌석 배열(100개)을 초기화한다.
4. `get_num_cores()`로 사용 가능한 CPU 코어 수 `n_cores`를 얻는다.
5. `n_cores`개의 워커 스레드를 만든다. 각 워커마다 self-pipe와 빈 PollSet을 부여한다.
6. listening socket을 만들고 `bind`/`listen`까지 끝낸다.
7. 메인 스레드는 STDIN과 listen socket을 `poll`로 감시한다.
   - STDIN에 `exit`/`quit`/EOF가 들어오면 자기 자신에게 SIGINT를 보내 종료 흐름으로 진입한다.
   - listen socket에 이벤트가 들어오면 `accept`로 연결을 받고, `find_suitable_pollset`으로 현재 등록된 클라이언트가 가장 적은 워커를 찾아 그 워커의 PollSet에 등록한다(`add_to_pollset`).
8. SIGINT가 수신되면 메인 루프를 빠져나와 `terminate_after_cleanup`을 호출한다.

### 4.3 워커 스레드 (`thread_func`)

각 워커는 자기 PollSet만을 `poll`하지만, 다른 스레드(메인 스레드의 `add_to_pollset`, 같은 스레드의 `remove_*`)에 의해 PollSet 내용이 바뀔 수 있다. 그래서 다음과 같은 구조를 사용한다.

```c
while (!sigint_received) {
  struct pollfd local_set[CLIENTS_PER_THREAD];
  nfds_t local_size;

  /* 1) lock → snapshot → unlock: 락은 최소 시간만 잡는다 */
  pthread_mutex_lock(&data->poll_set->mutex);
  local_size = data->poll_set->size;
  memcpy(local_set, data->poll_set->set,
         sizeof(struct pollfd) * data->poll_set->size);
  pthread_mutex_unlock(&data->poll_set->mutex);

  /* 2) snapshot에 대해 poll: 락을 잡지 않은 상태 */
  int32_t poll_result = poll(local_set, local_size, -1);
  ...
  /* 3) 이벤트 처리: receive_request/send_response 등은 락 밖에서 */
}
```

이 패턴은 PDF 명세의 두 조건을 동시에 만족시킨다.

- *"Mutex for poll set should not be held during socket read/write"* — 네트워크 I/O는 latency가 커서 락을 잡은 채로 하면 다른 스레드가 PollSet에 접근하는 것이 지연된다. snapshot 후 락을 풀고 I/O를 수행한다.
- *"When there is a file that is ready to be read, you have to lock the poll set"* — 처리 중에 PollSet이 바뀔 수 있으므로, fd를 통해 실제 PollSet 내 index를 다시 찾는다(`find_fd_in_pollset`).

### 4.4 self-pipe 패턴

워커가 `poll`에서 blocking 상태일 때 메인 스레드가 새 클라이언트를 추가하면, 워커가 즉시 그 fd를 감시 대상에 포함시켜야 한다. 그러나 `poll`은 매개변수로 받은 fd 목록만 보므로, 추가된 fd는 다음 `poll` 호출 때나 반영된다.

이를 해결하기 위해 워커마다 `pipe(pipe_fds[i])`로 파이프를 만들어 read end(`pipe_fds[i][0]`)를 PollSet의 첫 번째 fd로 등록한다. 메인 스레드는 새 클라이언트를 추가한 후 `notify_pollset`에서 write end에 1 byte를 써서 워커를 깨운다.

```c
void notify_pollset(int32_t notification_fd) {
  write(notification_fd, "", 1);
}
```

워커는 `poll`이 반환되면 자기 pipe_out_fd에서 들어온 알림 바이트를 그냥 비워내고 다음 iteration으로 넘어가는데, 다음 iteration에서 PollSet snapshot을 다시 뜨므로 새 fd가 자연스럽게 포함된다. 종료 시에도 메인 스레드는 모든 워커의 pipe write end에 byte를 쓰고 `close`하여 잠들어 있는 워커를 모두 깨운다.

### 4.5 CPU 코어 수 결정

PDF 슬라이드 7의 권장 방법을 따라 `sched_getaffinity`로 현재 프로세스가 사용할 수 있는 CPU 집합을 가져오고 `CPU_COUNT_S`로 개수를 센다.

```c
int32_t get_num_cores() {
  cpu_set_t cpu_set;
  sched_getaffinity(0, sizeof(cpu_set), &cpu_set);
  return CPU_COUNT_S(sizeof(cpu_set), &cpu_set);
}
```

이를 통해 컨테이너/VM이 일부 코어만 노출하는 경우에도 올바른 값을 얻는다.

### 4.6 새 클라이언트 분배: `find_suitable_pollset`

메인 스레드는 `accept` 후 다음 정책으로 분배한다.

- 모든 워커 PollSet 중 현재 size가 가장 작은(=클라이언트가 가장 적은) PollSet을 선택한다.
- 모든 PollSet이 `CLIENTS_PER_THREAD`만큼 가득 차 있으면 `-1`을 반환하고, 메인 루프는 잠깐 후 다시 시도한다.
- size 조회 시에도 각 PollSet의 mutex를 짧게 잡아 race condition을 방지한다.

이 정책은 PDF 슬라이드 10의 *"the thread with the fewest number of clients"* 요구사항과 일치한다.

## 5. 동기화 설계: 락 계층과 데드락 방지

### 5.1 락의 종류

서버에는 다음 4종류의 mutex가 존재한다.

| Mutex | 보호 대상 | 위치 |
|---|---|---|
| `Users.array_mutex` | `Users.array`, `Users.size` (배열 구조 자체) | 1개 |
| `Users.user_mutex[uid]` | 특정 사용자의 `logged_in` 상태 등 필드 | 사용자별 1개 (NUM_USERS = 10000) |
| `Seat[i].mutex` | i번째 좌석의 `user_who_booked`, `stats` | 좌석별 1개 (NUM_SEATS = 100) |
| `PollSet.mutex` | 한 워커 스레드의 PollSet | 워커별 1개 |

세분화된 락은 contention을 줄여 동시성을 높인다. 예를 들어 사용자 A가 좌석 1을 예약 중일 때, 사용자 B가 좌석 2를 예약하는 작업은 완전히 병렬로 진행된다.

### 5.2 락 획득 순서

데드락을 방지하기 위해 PDF 슬라이드 15의 권장 순서 *"user-array → user → seat"* 를 모든 핸들러에서 일관되게 유지한다. 예를 들어 `book` 처리는 다음 순서를 따른다.

1. `array_mutex` lock
2. `find_user`로 uid 찾기
3. `user_mutex[uid]` lock
4. `array_mutex` unlock (uid가 결정되었으므로 더 이상 배열 구조를 보지 않는다)
5. `seat->mutex` lock
6. seat 갱신
7. `seat->mutex` unlock → `user_mutex[uid]` unlock

이 패턴을 모든 핸들러에서 추출해 `lock_logged_in_user` 헬퍼로 만들었다.

```c
static pa3_uid_t lock_logged_in_user(const Request* request,
                                     Users* users,
                                     const char** active_user) {
  if (!request_matches_active_client(request, active_user)) return -1;

  pthread_mutex_lock(&users->array_mutex);
  pa3_uid_t uid = find_user(users, request->username);
  if (uid < 0) {
    pthread_mutex_unlock(&users->array_mutex);
    return -1;
  }
  pthread_mutex_lock(&users->user_mutex[uid]);
  pthread_mutex_unlock(&users->array_mutex);

  if (!users->array[uid].logged_in) {
    pthread_mutex_unlock(&users->user_mutex[uid]);
    return -1;
  }
  return uid; /* user_mutex를 잡은 채로 반환 */
}
```

호출자는 반환된 uid로 작업한 뒤 반드시 `pthread_mutex_unlock(&users->user_mutex[uid])`로 마무리한다.

### 5.3 PollSet mutex의 분리

PollSet mutex는 위 사용자/좌석 락과 별개의 계층에 있다. 워커 스레드는 다음 두 시점에만 PollSet mutex를 짧게 잡는다.

- snapshot을 뜰 때 (top of loop)
- 처리 중인 fd의 active_users index를 다시 찾을 때

`receive_request`/`handle_request`/`send_response`는 모두 PollSet mutex를 잡지 않은 상태에서 호출된다. 이로써 socket I/O가 길어져도 메인 스레드의 `add_to_pollset` 또는 같은 워커의 `remove_*`가 영향을 받지 않는다.

### 5.4 active_user 포인터의 안전성

`handle_request`에 넘기는 `active_user`는 `&data->poll_set->active_users[actual_i]`의 주소다. 이 주소는 PollSet mutex 밖에서 사용되지만, 다음 두 가지 이유로 안전하다.

- `active_users[i]` 배열의 메모리 주소는 PollSet이 free되기 전까지 유효하다 (배열이므로 realloc/이동이 없다).
- 한 fd의 active_users[i]를 수정·해제할 수 있는 주체는 같은 워커 스레드뿐이다. 다른 워커는 다른 PollSet을 가진다. 메인 스레드는 `add_to_pollset`에서 append만 하고, 기존 index에 손대지 않는다.

### 5.5 데드락 시나리오 검토

- `book`/`cancel-booking`: 항상 user → seat 순서 → ✓
- `confirm-booking`: user → seat 순서로 모든 좌석을 순회하는데, 각 seat lock을 한 번에 하나씩만 잡고 풀므로 hold-and-wait 사이클이 없다. → ✓
- `login`: array → user, 새 사용자 등록 시에도 array를 먼저 잡고 add_user한 뒤 user lock을 잡는다. → ✓
- `logout`: array → user 순서. → ✓
- `deactivate_user`: array → user. 클라이언트 연결 끊김 처리 중 호출되는데, 같은 순서를 따른다. → ✓

모든 경로가 항상 `array → user → seat` 순서로 락을 잡고, lock-hold 중에는 더 낮은 순서의 락만 추가로 잡으므로 데드락이 생길 수 없다.

## 6. 사용자·비밀번호 관리 (Argon2id)

### 6.1 Users 구조체

```c
typedef struct {
  User*            array;        /* 등록된 사용자 배열 */
  size_t           size;         /* 현재 사용 중 */
  size_t           capacity;     /* NUM_USERS = 10000 */
  pthread_mutex_t  array_mutex;
  pthread_mutex_t* user_mutex;   /* user_mutex[uid]를 사용자별 lock으로 */
} Users;
```

`setup_users`는 capacity만큼의 `User` 배열과 `user_mutex` 배열을 미리 동적 할당한다. 사용자별 mutex를 미리 초기화하면 사용자 등록 시 mutex 초기화를 빠뜨릴 위험이 없고, 등록과 동시에 그 사용자의 mutex를 잡을 수 있다.

### 6.2 비밀번호 해시 (Argon2id)

PDF 슬라이드 24의 요구사항에 따라 평문 비밀번호는 저장하지 않고, `hash_password`로 Argon2id 해시를 생성한 뒤 인코딩된 문자열만 보관한다.

```c
void hash_password(const char* password, char* hashed_password) {
  uint8_t salt[SALT_SIZE];
  generate_salt(salt);                           /* getrandom으로 salt 생성 */
  char hash[HASHED_PASSWORD_SIZE];
  argon2id_hash_encoded(2, MEMORY_USAGE, 1,
                        password, strlen(password),
                        salt, SALT_SIZE,
                        HASH_SIZE, hash, HASHED_PASSWORD_SIZE);
  strncpy(hashed_password, hash, HASHED_PASSWORD_SIZE);
  hashed_password[HASHED_PASSWORD_SIZE - 1] = '\0';  /* 안전한 NUL terminate */
}
```

검증은 `argon2id_verify`를 통해 수행한다(`validate_password`). 동일한 비밀번호여도 salt가 다르므로 동일 해시 문자열이 나오지 않는다는 점을 활용한다.

### 6.3 `__has_include` 기반 폴백

`server/helper.c` 상단에는 `argon2.h`가 시스템에 없을 때 함수를 외부 심볼로 직접 선언하는 폴백 블록을 두었다. 헤더가 없어도 라이브러리(`libargon2.so.1` 등)만 있으면 링크 단계에서 해결된다.

```c
#if __has_include(<argon2.h>)
#include <argon2.h>
#else
#define ARGON2_OK 0
int argon2id_hash_encoded(...);
int argon2id_verify(...);
#endif
```

### 6.4 로그인 상태 표시

`User.logged_in`은 `bool`이며, 다음 순서로만 조작한다.

- `true`로 설정: 로그인 성공 시(`handle_login_request`), `user_mutex[uid]`를 잡은 상태에서.
- `false`로 설정: 로그아웃(`handle_logout_request`) 또는 연결 끊김(`deactivate_user`) 시, 동일하게 `user_mutex[uid]`를 잡은 상태에서.

## 7. 좌석 자료구조와 예약 동기화

### 7.1 좌석 구조체

```c
typedef struct {
  pa3_seat_t id;
  uint64_t   amount_of_times_booked;
  uint64_t   amount_of_times_canceled;
} SeatStats;

typedef struct {
  SeatStats        stats;
  const char*      user_who_booked;
  pthread_mutex_t  mutex;
} Seat;
```

`default_seats`에서 100개의 `Seat`를 할당하고 각 mutex를 초기화한다. 좌석 번호는 1..100, 배열 index는 0..99이므로 항상 `seats[seat_number - 1]`로 접근한다.

### 7.2 예약/취소의 race 처리

여러 클라이언트가 같은 좌석을 동시에 예약 시도하면, 단 한 명만 성공해야 한다. `handle_book_request`는 다음과 같다.

```c
pthread_mutex_lock(&seat->mutex);
if (seat->user_who_booked != nullptr) {
  pthread_mutex_unlock(&seat->mutex);
  pthread_mutex_unlock(&users->user_mutex[uid]);
  return BOOK_ERROR_SEAT_UNAVAILABLE;
}
seat->user_who_booked = strdup(request->username);
seat->stats.amount_of_times_booked++;
pthread_mutex_unlock(&seat->mutex);
```

좌석 mutex가 critical section을 보호하므로, 두 스레드가 동시에 진입해도 한 쪽은 `user_who_booked != nullptr` 검사에서 막힌다. 취소도 같은 패턴으로 처리한다.

### 7.3 `query`의 일관성

`query`는 read-only지만 `SeatStats`를 통째로 응답해야 하므로, seat mutex를 잡은 상태에서 로컬 `stats`로 복사한 뒤 mutex를 풀고 응답한다.

```c
pthread_mutex_lock(&seat->mutex);
SeatStats stats = seat->stats;        /* 복사: tearing 방지 */
pthread_mutex_unlock(&seat->mutex);
```

복사한 stats는 더 이상 공유 자원이 아니므로 안전하게 직렬화·전송한다.

### 7.4 `confirm-booking`의 순회

좌석 1..100을 순서대로 돌면서 각 좌석 mutex를 따로 잡아 검사한다. 모든 seat mutex를 한꺼번에 잡지 않으므로 contention이 적고, 결과 배열도 좌석 번호의 오름차순으로 자연스럽게 정렬된다(클라이언트가 출력 시 정렬을 따로 할 필요가 없다).

## 8. Action별 처리 흐름

### 8.1 Action 0 — Termination

명세 슬라이드 20에 따라 클라이언트는 termination 요청을 서버로 보내지 않는다. 클라이언트는 입력에서 `exit`/`quit`을 만나면 main loop를 빠져나오고, 그 시점에 active user가 있으면 `terminate`에서 `LOGOUT` request를 자동으로 보낸다. 그 다음 socket을 close한다.

만약 잘못된 구현으로 서버가 action 0 요청을 받게 되면 `handle_request`의 default branch에서 `-1`을 응답하고, 클라이언트는 "Invalid action received!"를 출력한다. 슬라이드 18의 *"If action id is not in the range of [1, 6], return -1"* 요구사항을 만족한다.

### 8.2 Action 1 — Login

처리 순서:

1. `*active_user != nullptr`이면 → `LOGIN_ERROR_ACTIVE_CLIENT`. (이미 다른 사용자가 이 클라이언트에 로그인 중)
2. username 없으면 → `LOGIN_ERROR_NO_USERNAME_AND_PASSWORD`.
3. password 없으면 → `LOGIN_ERROR_NO_PASSWORD`.
4. username으로 사용자 검색.
   - **기존 사용자**: 이미 `logged_in`이면 `LOGIN_ERROR_ACTIVE_USER`. 그렇지 않으면 `validate_password`로 검증, 성공 시 `logged_in = true` + active_user 갱신, 실패 시 `LOGIN_ERROR_INCORRECT_PASSWORD`.
   - **신규 사용자**: `hash_password`로 해시 생성 후 `add_user`로 등록, `logged_in = true`로 설정하고 active_user 갱신.

`save_active_user`는 strdup된 사본을 `active_user`에 저장한다. 이 메모리는 logout 시 또는 PollSet에서 fd가 제거될 때 free된다.

PDF 슬라이드 27의 모든 에러 케이스(ACTIVE USER, ACTIVE CLIENT, INCORRECT PASSWORD, NO PASSWORD)와 일치한다.

### 8.3 Action 2 — Book

처리 순서:

1. data가 없으면 → `BOOK_ERROR_NO_DATA`.
2. data를 `parse_seat_number`로 파싱: `strtoull`로 숫자 변환, 1..100 범위 검증. 잘못된 형식이거나 범위를 벗어나면 → `BOOK_ERROR_SEAT_OUT_OF_RANGE`.
3. `lock_logged_in_user`로 active_user/uid 확인. 실패하면 → `BOOK_ERROR_USER_NOT_LOGGED_IN`.
4. 해당 좌석 mutex를 잡고:
   - 이미 예약자가 있으면 → `BOOK_ERROR_SEAT_UNAVAILABLE`.
   - 비어 있으면 username 사본을 저장하고 `amount_of_times_booked++`.

### 8.4 Action 3 — Confirm booking

처리 순서:

1. data가 없으면 → `CONFIRM_BOOKING_ERROR_NO_DATA`.
2. data가 `"available"` 또는 `"booked"`가 아니면 → `CONFIRM_BOOKING_ERROR_INVALID_DATA`.
3. `lock_logged_in_user`로 검증.
4. 좌석 1..100을 순회하며 조건에 맞는 좌석 id를 `selected[]` 임시 배열에 모은다.
   - `available`: `user_who_booked == nullptr`
   - `booked`: `user_who_booked == request->username`
5. count > 0이면 `pa3_seat_t` 배열을 malloc하고 memcpy하여 응답 데이터로 보낸다.

### 8.5 Action 4 — Cancel booking

처리 순서:

1. data 없음 / 좌석 번호 파싱 실패 / 로그인 안 됨 → 각각의 에러 코드.
2. 좌석 mutex를 잡고:
   - 예약자가 없거나 예약자가 다른 사용자면 → `CANCEL_BOOKING_ERROR_SEAT_NOT_BOOKED_BY_USER`.
   - 예약자가 맞으면 `user_who_booked` 문자열을 free하고 `nullptr`로 설정, `amount_of_times_canceled++`.

### 8.6 Action 5 — Logout

처리 순서:

1. username 없으면 → `LOGOUT_ERROR_USER_NOT_FOUND`.
2. array를 잡고 사용자 검색, 없으면 → `LOGOUT_ERROR_USER_NOT_FOUND`.
3. user_mutex 잡고 array unlock.
4. `logged_in == false`이거나 이 클라이언트의 active_user와 일치하지 않으면 → `LOGOUT_ERROR_USER_NOT_LOGGED_IN`.
5. `logged_in = false` 설정 + `*active_user`를 free하고 nullptr로 설정.

### 8.7 Action 6 — Query

명세 슬라이드 37에 query는 `USER NOT LOGGED IN` 에러가 없다. 즉, 로그인 없이도 수행 가능하다. 클라이언트의 `parse_request`도 query인 경우 active_user 검증을 건너뛴다.

처리 순서:

1. data 없음 / 좌석 번호 파싱 실패 → 각각의 에러.
2. 좌석 mutex 잡고 `SeatStats`를 로컬로 복사 → mutex 풀고 응답 data로 전송.

응답 데이터는 문자열로 변환하지 않고 `SeatStats` 구조체 그대로 보낸다(슬라이드 36 *"Do not convert to string"*).

### 8.8 Action handler 디스패치

`handle_request`는 단순 switch이다. `default` 또는 `ACTION_TERMINATION`은 코드 `-1`로 응답하며, 워커 스레드는 stderr에 `Invalid action received: <action_id>`를 출력한다(슬라이드 11).

## 9. 클라이언트 설계

### 9.1 두 가지 실행 모드

`main`은 인자 개수에 따라 mode를 결정한다.

- **File mode** (`argc > 3`): 인자 file을 line 단위로 읽어 `evaluate`로 한 줄씩 처리하고, EOF에 도달하면 자동 종료한다. `getline` 사용 시 메모리 누수가 없도록 line 사용 후 free 처리한다.
- **Interactive mode**: `readline("")`로 한 줄씩 입력받고, `add_history`로 입력 기록을 저장한다. `readline`이 NULL(EOF)을 반환하거나 SIGINT가 들어오면 종료한다.

두 mode 모두 main loop 종료 후 `terminate(sockfd, active_user)`를 호출한다.

### 9.2 입력 파싱 (`parse_request`)

`to_action`은 입력의 첫 토큰에서 공백·구두점을 모두 제거한 뒤(`isspace`, `ispunct`), 정해진 문자열과 비교한다. 그래서 `confirm-booking`, `confirm booking`, `confirmbooking` 같은 변형 입력이 모두 같은 action으로 정규화된다.

`parse_request`는 다음 client-side validation을 수행한다.

| 케이스 | 처리 |
|---|---|
| action이 인식 불가 | `Invalid action received!` 출력, 서버 호출 없음 |
| `login`인데 이미 active_user가 있음 | `Client is already serving user X!` 출력, 서버 호출 없음 |
| `exit`/`clear` | 서버 호출 없음 (각각 종료/화면 지우기) |
| `query` | active_user 검증 생략 (login 불필요) |
| 그 외 (book/cancel/confirm/logout) | active_user 없으면 `User is not logged in!` 출력, 서버 호출 없음 |

이 사전 검증 덕분에 서버에 불필요한 트래픽이 가지 않고, 명세의 예제(슬라이드 39)에서 `book 12 → User is not logged in!`가 정확히 재현된다.

`login`은 두 번째·세 번째 토큰을 각각 username과 password로 채우고, 그 외 action은 두 번째 토큰을 data로 채운다.

### 9.3 응답 처리 (`handle_response`)

각 action별로 `handle_*_response` 함수를 둔다. 응답 코드를 보고 성공이면 stdout, 실패면 stderr에 명세된 문구로 출력한다.

- `login` 성공 시 `*active_user`에 username 사본을 저장한다.
- `logout` 성공 시 `*active_user`가 같은 username이면 free하고 nullptr로 설정한다(이중 logout 방지).
- `confirm-booking` 성공 시 응답 data를 `pa3_seat_t[]`로 캐스팅해서 `, `로 구분된 좌석 목록을 출력한다.
- `query` 성공 시 응답 data를 `SeatStats`로 memcpy한 뒤 횟수에 따라 단·복수형(`time` vs `times`)을 선택한다.

### 9.4 자동 logout (`terminate`)

클라이언트가 종료할 때 active_user가 남아 있으면 자동으로 `LOGOUT` request를 보낸 뒤 socket을 close한다. 이로써 클라이언트가 정상 종료한 경우 서버의 user 상태도 logged-out으로 동기화된다. (비정상 종료의 경우는 서버가 socket close를 감지해서 `remove_from_pollset` → `deactivate_user`로 정리한다.)

## 10. Error handling 정책

### 10.1 출력 채널

- **성공 메시지**: `stdout` (`printf`)
- **실패 메시지**: `stderr` (`fprintf(stderr, ...)`)

PA3 명세 슬라이드 19의 *"On the client, print to stdout on success and to stderr on failure"* 와 일치한다.

### 10.2 에러 코드 enum

`include/pa3_error.h`에 action별 에러 코드를 enum으로 정의했다. 첫 값은 항상 `*_SUCCESS = 0`이다. 명세 슬라이드 27/29/31/33/35/37의 모든 에러를 enum 값으로 반영했다.

### 10.3 client-side vs server-side 책임 분리

- **클라이언트가 단독으로 판단 가능한 경우는 서버에 보내지 않는다.** 예: 로그인 안 된 상태에서 book.
- **서버 상태가 필요한 경우는 무조건 서버가 결정한다.** 예: 좌석 예약 가능 여부, 비밀번호 일치 여부.

### 10.4 비정상 연결 처리

워커 스레드는 다음을 감지해서 fd를 PollSet에서 제거하고 active_user를 정리한다.

- `POLLERR`, `POLLHUP`, `POLLNVAL` revents
- `receive_request`/`send_response` 실패 (read 0 또는 -1)

`remove_from_pollset` → `deactivate_user`로 서버의 `User.logged_in`도 false로 되돌리므로, 클라이언트가 갑자기 죽어도 해당 사용자가 영원히 logged-in 상태로 남는 문제가 없다.

## 11. 자원 정리와 종료 처리

### 11.1 SIGINT 처리

`common/helper.c`의 시그널 핸들러는 단순히 전역 `sigint_received = true`만 설정한다. async-signal-safe하지 않은 함수를 핸들러에서 호출하지 않으려는 의도다. 메인 스레드와 워커 스레드는 main loop 진입 전에 `!sigint_received` 조건을 검사하며, `poll`은 EINTR로 깨어나면 `continue`로 다시 조건 검사로 돌아간다.

### 11.2 STDIN 기반 종료

서버 메인 스레드는 STDIN도 poll 대상으로 둔다. `check_stdin_for_termination`이 `exit`/`quit`/EOF/빈 줄 중 하나를 감지하면 `kill(getpid(), SIGINT)`로 SIGINT를 자기 자신에게 보낸다. 결과적으로 SIGINT 경로와 stdin 경로가 동일한 종료 흐름으로 수렴한다.

### 11.3 `terminate_after_cleanup`

종료 단계는 다음 순서로 진행한다.

1. **워커 깨우기**: 각 워커의 pipe write end에 1 byte를 쓰고 close한다. 워커는 `poll`에서 깨어나 `!sigint_received`로 루프를 빠져나가고 `pthread_exit`한다.
2. **`pthread_join`**: 각 워커 스레드가 완전히 종료할 때까지 기다린다.
3. **PollSet 내부 자원 해제**: pipe read end를 close하고, 살아 있는 클라이언트 소켓을 `close`하고, 살아 있는 `active_users[j]` 문자열을 free한다. 그 다음 PollSet mutex를 destroy하고 PollSet 자체를 free한다.
4. **좌석 정리**: 각 좌석의 mutex를 destroy하고, 남아 있는 `user_who_booked` 문자열을 free한 뒤 배열을 free한다.
5. **나머지 정리**: listen socket close, tid_arr/data_arr/pipe_fds free, `free_users`로 사용자 배열·mutex 배열·username/hashed_password 문자열 모두 free.
6. `puts("Server terminated!")` 출력.

특히 3번 단계의 *살아 있는 클라이언트 소켓과 active_users 문자열 정리* 는 valgrind 누수를 막기 위한 핵심이다. 정상 종료한 클라이언트는 자동으로 logout + close하지만, 서버 종료 시점에 아직 연결되어 있는 클라이언트가 있을 수 있다.

### 11.4 클라이언트의 자원 정리

- `parse_request`는 input/input_copy/error 경로에서의 Request 모두 안전하게 free한다.
- `evaluate`는 매번 Request/Response를 free한다.
- 종료 직전 `terminate`에서 logout request의 Request/Response도 free한다.
- main 종료 직전 socket을 close한다.

## 12. 스켈레톤 대비 구현/수정한 부분 요약

스켈레톤(`pa3_skeleton_code.tar.zst`)에는 함수 시그니처·자료구조·일부 헬퍼만 있고 핵심 로직은 비어 있었다(주로 `// ???` 또는 빈 함수). 본 구현에서 작성·수정한 부분은 아래와 같다.

### 12.1 새로 작성한 함수 (server)

- `add_to_pollset` — PollSet에 클라이언트 fd append + notify.

## 13. 테스트 및 검증

### 13.1 빌드 검증

`make clean && make`를 실행하여 다음과 같이 깨끗하게 컴파일된다(경고 0개, `-Werror` 통과).

```
gcc -Wall -Wextra -Wpedantic -Werror -ggdb -std=gnu2x -D_GNU_SOURCE -Iinclude
    -c -o server/handle_request.o server/handle_request.c
...
gcc ... -o pa3_server server/handle_request.o server/helper.o server/pa3_server.o
        common/helper.o -l:libargon2.so.1
...
gcc ... -o pa3_client client/handle_response.o client/helper.o client/pa3_client.o
        common/helper.o -ledit
```

`ls | grep pa3` 결과: `pa3_server pa3_client` (명세 슬라이드 5 요구사항 충족).

### 13.2 Example 1 (PDF 슬라이드 39) 재현

다음 입력 파일을 file mode로 실행했다.

```
book 12
logout
confirm-booking
login user password
book 42
book 1025
aaa
logout
login AzureDiamond hunter2
book 42
book 13
book 98
confirm-booking booked
logout
login user abc
```

**STDOUT (성공 메시지)**

```
User user logged in successfully!
Seat 42 was booked successfully by user user!
User user logged out successfully!
User AzureDiamond logged in successfully!
Seat 13 was booked successfully by user AzureDiamond!
Seat 98 was booked successfully by user AzureDiamond!
Booked seats by user AzureDiamond: 13, 98
User AzureDiamond logged out successfully!
```

**STDERR (실패 메시지)**

```
User is not logged in!
User is not logged in!
User is not logged in!
Seat 1025 is out of range [1,100]!
Invalid action received!
Seat 42 is unavailable for booking!
User user provided incorrect password!
```

명세 슬라이드 39의 예상 출력과 한 줄도 빠짐없이 일치한다.

### 13.3 Example 2 (동시 클라이언트) 재현

PDF에 포함된 `run-example2-client.sh`를 실행하여 두 클라이언트가 동시에 접속·로그인·예약·취소·query를 수행하는 시나리오를 검증했다. 검증 포인트:

- 클라이언트 1이 user로 로그인한 상태에서 클라이언트 2가 같은 user로 로그인 시도 → `User user is already logged in!` 또는 `Client is already serving user user!` (race에 따라).
- 두 클라이언트가 같은 좌석 42를 동시에 book → 한 쪽만 성공, 다른 쪽 `Seat 42 is unavailable for booking!`.
- 한 쪽이 취소 후 다른 쪽이 다시 book → 성공.
- `query 42` 응답이 누적 예약/취소 횟수를 정확히 반영.
- 잘못된 비밀번호로 재로그인 시 `User user provided incorrect password!`.

모든 시나리오에서 예상된 응답이 나오고, 서버는 정상 종료된다.

### 13.4 동시성 race 검증

여러 클라이언트가 동시에 같은 좌석을 예약하려 하면 정확히 한 클라이언트만 성공해야 한다. 8개의 클라이언트가 동시에 `book 77`을 보냈을 때, stdout에는 `Seat 77 was booked successfully by user ...!`이 정확히 1번, stderr에는 `Seat 77 is unavailable for booking!`이 7번 출력되었다. 직후 `query 77`은 `Seat 77 was booked 1 time and canceled 0 times!`를 반환하여, seat mutex가 경쟁을 올바르게 직렬화하고 있음을 확인했다.

### 13.5 종료/cleanup 검증

다음 시나리오로 정상 종료를 확인했다.

- **모든 클라이언트가 정상 logout 후 종료한 경우**: 서버에 SIGINT를 보내면 `Server terminated!` 출력 후 정상 종료.
- **클라이언트가 logout 없이 갑자기 죽은 경우**: 워커가 `POLLHUP`을 감지하여 `remove_from_pollset` → `deactivate_user`로 사용자 상태를 정리. 이후 서버 SIGINT 시 정상 종료.
- **클라이언트가 연결된 상태에서 서버 SIGINT를 받은 경우**: `terminate_after_cleanup`이 PollSet에 남아 있는 클라이언트 socket을 close하고 active_user 문자열을 free한다. 서버는 정상 종료한다(crash/hang 없음).

### 13.6 메모리 검증

`-ggdb`로 빌드한 상태에서 valgrind를 실행하여 누수를 확인하였다.

```
valgrind --leak-check=full --track-origins=yes --show-leak-kinds=all \
    ./pa3_server <port>
valgrind --leak-check=full --track-origins=yes --show-leak-kinds=all \
    ./pa3_client <ip> <port> <input_file>
```

- 서버: definitely lost / indirectly lost / possibly lost 모두 0 byte. `ERROR SUMMARY: 0 errors from 0 contexts`.
- 클라이언트: `editline` 라이브러리 내부의 still-reachable 외에는 모두 0 byte. definitely lost / indirectly lost / possibly lost 모두 0 byte. `ERROR SUMMARY: 0`.

명세 슬라이드 3의 *"Resources allocated dynamically should be freed before the program terminates"* 요구사항을 충족한다.

## 14. 결론

본 PA3 구현은 PDF 명세에서 요구한 모든 항목을 다음과 같이 달성하였다.

- **포팅 가능성과 빌드**: `make` 한 번으로 `pa3_server`, `pa3_client`가 빌드되며, libargon2의 두 가지 설치 형태(`.so`, `.so.1`)를 자동으로 처리한다.
- **멀티스레드 구조**: CPU 코어 수만큼의 워커 스레드가 각자의 PollSet을 가지고 클라이언트를 polling하며, 메인 스레드는 가장 한가한 워커에게 새 연결을 배정한다.
- **동시성 안전성**: array → user → seat 순서로 정렬된 4계층 mutex 시스템을 통해 데드락 없이 race condition을 방지한다. PollSet mutex는 socket I/O 동안 잡지 않는다.
- **사용자/비밀번호 관리**: 최대 10000명의 사용자를 in-memory 배열로 관리하고, Argon2id로 해시된 비밀번호만 저장한다.
- **6개 Action 모두 구현**: login, book, confirm-booking, cancel-booking, logout, query 모두 명세된 에러 코드와 메시지 포맷에 맞춰 동작한다. termination(action 0)은 클라이언트가 서버로 보내지 않으며, 잘못된 action이 들어와도 `-1`로 안전하게 응답한다.
- **클라이언트 두 가지 모드**: file mode와 interactive mode 모두 지원하며, 종료 시 자동 logout으로 서버 상태를 동기화한다.
- **자원 정리**: 동적 메모리, 소켓, 스레드, mutex 모두 종료 전에 해제되며 valgrind에서 누수 0이 확인되었다.
- **명세 출력 포맷 준수**: 성공/실패 stream 분리 및 메시지 문자열 모두 PDF 슬라이드 39의 예제와 정확히 일치한다.

이상으로 PA3 구현 보고서를 마친다.
